## What was checked and held up

- **`main.js:648-694` submit wrapper.** Traced every form with a `.datepicker-input` (service record, complete workplan, incident, workplan, component status/overview/details, quick swap, collection status, plan/complete services, edit installation record) to work out, for each, whether the shared wrapper is the terminal `onsubmit` handler or gets overwritten by the form's own handler, and whether the plan/complete-services and quick-swap/collection-status "forms" even go through the `submit` event at all. They don't: those four have no `<form>`/use `type="button"` and post via `fetch` after their own click-handler validation, so the wrapper is inert for them. Incident, workplan and the three component forms overwrite `form.onsubmit` themselves immediately after the wrapper runs, so the wrapper's body never actually fires for them either, in both the old and new code. The only forms where the wrapper is the terminal handler are `serviceRecordForm`, `completeWorkplanForm` and `editHistoryForm`. For those, the old code always called `form.submit()` itself once dates were syntactically valid, which bypasses the native `submit` event, so any `addEventListener('submit', ...)` business-rule listener registered after it (both `serviceRecordForm`'s and `completeWorkplanForm`'s date/required checks) never got a chance to block the request. The new code only calls `e.preventDefault()` on the invalid path and otherwise returns whatever `originalSubmit` returns (or lets the browser submit natively), so those listeners now run and can block. Checked all templates the wrapper newly hands to native submission for `required` attributes on conditionally-hidden fields (the classic "not focusable" crash) - none found; the only conditionally-hidden required field (`resolution_date`, `completion_date` on incident/workplan) sits in a form that owns its `onsubmit` and calls `.submit()` manually, which bypasses native validation same as before. No regression found; this is a correct, well-targeted fix.

- **`db_migration.py` step ordering.** `run_all_migrations` runs steps 12-17 in exactly the order the handover claims: columns added (12), notes column (13), workplan services (14), incident links (15), then the workplans/incidents table rebuild (16), then `workplan_name` added (17). Confirmed the rebuild in step 16 has no `workplan_name` in its fixed column list, which is correct only because it always runs before step 17. Traced idempotency of every one of the 17 steps; all guard on a `check_*` presence test before writing. Verified the `[n/17]` print numbering has no gaps or duplicates. No issue.

- **`utils.py` tuple shapes.** `get_incident_data_tuple` returns 17 fields, `get_workplan_data_tuple` 14, `get_planned_service_data_tuple` 11. Grepped every Jinja unpack site (`bike_details.html`, `component_details.html`, `incident_reports.html`, `workplan_details.html`, `modal_service_record.html`, `modal_plan_services.html`, `workplans.html`) - all match field-for-field and in order. No stale unpack found.

- **`business_logic.py` new parameters.** `create_workplan`'s `source_incident_id`/`component_ids` path narrows the incident's components to the ones still selected and degrades gracefully (message, not failure) when none remain. `update_workplan`'s partial-update dict omits `workplan_name` entirely, so `Workplans.update(**data)` (a real partial update in Peewee) never touches it on `update_mode=partial` (used by "Complete workplan"); the full-update path clears the name to `None` on an empty field, which `resolve_workplan_title` then correctly falls back on. `change_collection_status`'s `notes` is passed straight through to the existing `create_history_record` per component, no new write path invented. `update_history_record`'s `notes` follows the same blank-to-`None` normalization as the rest of the file. Verified `recalculate_component_after_service_removal` is genuinely shared between `delete_record` (Planned services skip it entirely, Completed ones call it) and the Completed-to-Planned branch of `update_service_record`, and that the previously-reported "`process_service_records` called without `workplan_id`" bug is fixed at both call sites.

## Issues found (none blocking)

1. **Minor - dead code.** `database_manager.py:362 read_all_services_by_component` and `:387 read_all_planned_services` are new, unused outside their own definitions; the former is only referenced by `tests/test_service_status.py`, the latter by nothing at all. Either wire them into a page/route or drop them.
2. **Minor - inconsistent field declaration.** `database_model.py: Workplans.workplan_name = CharField(null=True)` is the only field in the whole model using `null=True`. The other three fields added in this same branch (`Services.status`, `Services.incident_id`, `Services.planned_date`, `ComponentHistory.notes`) are plain `CharField()`, matching the design doc's own stated rule ("All new fields declared as plain CharField(), matching existing style"). Functionally inert here (SQLite's `ALTER TABLE ADD COLUMN` never enforces `NOT NULL` regardless of what the ORM declares), but it is a needless deviation from a rule the branch itself set.
3. **Minor - readability.** `db_migration.py: migrate_incidents_workplan_link`'s guard (`if not check_services_integration_columns(cursor): skip`) is a double negative (skip when the missing-columns list is empty) that takes real effort to trace. A one-line code comment stating why would help; the print message already explains it to a human running the tool, just not a reader of the diff.
4. **Minor - performance.** `derive_workplan_context` (one `read_component`/`read_bike_name` per service) is computed twice per page render on `bike_details`, `component_details`, `incident_reports` and `workplan_details`: once inside `get_workplan_names_dict()` for title resolution, again inside `get_workplan_data_tuple()` for the workplans table. This matches the approved design (`get_workplan_names_dict` was explicitly "unchanged") and the production regression run showed no problem at current scale (~200 services, dozens of workplans), so not a blocker, but worth a follow-up to compute the context once and reuse it.
5. **Minor - pre-existing pattern, wider surface.** `renderIncidentServices` in `main.js` builds table rows via `innerHTML` template literals that interpolate `service.component_name`, `service.description` and now `service.workplan_name` unescaped. This is consistent with 8 other pre-existing `innerHTML` template-literal sites already in `dev`'s `main.js`, so it is not a new deviation, but `workplan_name` is the first genuinely free-text, user-authored field (per decision D1) to flow through this particular sink. Worth folding into the "duplication in templates and JavaScript" item already tracked in `TECHNICAL_DEBT.md` rather than fixing ad hoc here.
